# Собственный динамик T23N: выбор голосового транспорта без облака

| Путь | Нагрузка/задержка | Статус |
|---|---|---|
| Hombo3 TTS → SSH → `/usr/sbin/play` → `rac` | Новый SSH-сеанс на каждую фразу, кодирование/загрузка PCM. Зато нет небезопасного аудио HTTP-порта и используется готовая штатная утилита. | **Первый безопасный вариант для физического теста** |
| Постоянный SSH-сеанс / Linux ControlMaster | Убирает повторное SSH-рукопожатие при частых ответах, но требует контроля переподключения и живого процесса `rac`. | Только после базового теста. Нативный SSH клиента Hombo3 под Windows может не поддерживать Unix-сокеты ControlMaster. |
| ONVIF/RTSP audio backchannel | Потенциально лучше для потока PCM/Opus и меньших задержек, но требует подтверждения совместимого Raptor, клиентского send-backchannel, кодека и усилителя. | Не считать готовым без проверки реальной камеры. |
| WebRTC RWD с двухсторонним аудио | Имеет низколатентный канал и сложность TLS/signaling, увеличивает rootfs/потребление памяти. | Опция `WIFICAM_WEBRTC=1` при сборке только после измерений. |
| Сырой UDP или неаутентифицированный HTTP `/speaker` | Минимальный код, но нет аутентификации/целостности и нет гарантии правильной буферизации. | **Не рекомендовано** |

Порядок приёмки: `microphone status` → наличие аудиодорожки RTSP → `speaker status`, `rac`, `play` → краткий слышимый тест. Если `ao_enabled=false`, значение менять/перезапускать Raptor только после отдельного бэкапа конфигурации и восстановления SSH; стенд Helper **никогда** это не делает.

У Hombo3 уже есть `backend/app/camera_speaker.py`, но он может лишь подтвердить код завершения SSH-процесса, а не факт слышимого воспроизведения. В штатной Windows реализации Hombo3 не следует слепо добавлять `ControlMaster` без проверки поддержки Windows OpenSSH. Полный диалог требует ещё VAD, шумоподавления/эхокомпенсации и согласования галочки WIFICAM с настройкой Hombo3.
